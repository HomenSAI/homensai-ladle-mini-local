# Mini Local 0.3.0 — архитектура

## Граница

Один магазин, один локальный телефон/планшет. Без backend, сетевых аккаунтов, REST API, FCM, клиентского приложения, распределённого остатка и синхронизации. Нет обещания одновременной работы на нескольких устройствах. Импорт резервной копии заменяет состояние, а не сливает его.

```text
Android MainActivity
  ├─ AssetPolicy: разрешённые файлы APK, блокировка внешних переходов
  ├─ локальный WebView: ui + i18n + styles + catalog-data
  │                       └─ core: команды, валидация, расчёты
  │                           storage: атомарное сохранение / backup crypto
  └─ LadleNative bridge
       ├─ AppDatabase + SnapshotValidator → SQLite
       ├─ SAF → файл зашифрованной копии
       └─ PhotoImporter → ограниченный JPEG без исходных метаданных
```

Это Java + локальный WebView, не Kotlin/Compose. APK не загружает сайт. BrowserRepository применяется только к демонстрации; Android подтверждённые записи хранятся через SQLite.

## Данные v3

Shop: контакты, адрес, язык, скин, EUR. Event: дата, время, название, ассортимент, closed. Catalog: трёхъязычный шаблон, категория, иллюстрация, nullable-цена, единица, активность/архив, optional JPEG. Customer: имя, фамилия, телефон, примечание. Order: клиент/событие, frozen lines, отмена, sale, payment, даты изменений. Audit: id, ISO timestamp, действие, подпись локального оператора (контактное лицо магазина), идентификаторы и сводка изменения.

Один заказ одного клиента на событие. Дополнения к предзаказу редактируют его, не создают дубликат. Для дополнительных фактических покупок используются дополнительные sale.lines из ассортимента этой даты, не переписывается первоначальная заявка. Самостоятельная анонимная кассовая продажа не входит в Mini Local.

Снимки имён/цен/единиц заказа сохраняются. Использованную единицу в дате менять нельзя. Отключение товара останавливает новые заказы, но не мешает выдаче старых. При удалении использованного шаблона он архивируется, а история остаётся.

## Числа

Все цены и полученные суммы — целые центы. Поле `grams` ради совместимости называется по-старому, но содержит **тысячные доли выбранной единицы**: для кг — граммы, для литра — миллилитры, для piece/pack — 1000 на каждую штуку/упаковку. При единице piece/pack значение обязано делиться на 1000. При отсутствии поля unit в старой записи применяется kg. Не использовать grams без unit как физический вес.

`lineTotal = (quantity_milli × price_cents + 500) / 1000` с целочисленным делением; JS использует BigInt. Округление half-up по каждой строке, после чего суммы складываются. Отдельного налогового расчёта нет: вводится конечная цена.

Сводка объединяет деньги, но количества группирует по единицам. Legacy plannedGrams/soldGrams содержат только kg. Сортировка заказов по весу также только kg; сортировка количества товаров сначала по единице.

## План, выдача, деньги

`sale=null` — факт не введён. `sale.complete=false` — частичная выдача. Полная выдача завершает обязательство даже при меньшем весе. Все исходные позиции указаны в факте явно, ноль допустим. Частичная и полная выдача записываются накопительно, не как отдельные события-порции.

`payment.amount` — всего получено, `method` cash/card/other, timestamp. Получение денег не выводится из выдачи. Нельзя оплатить предзаказ без факта или превысить сумму факта; авансы/депозиты не поддерживаются. Отрицательные платежи не вводятся: после внешнего возврата оператор уменьшает накопительную сумму, изменение фиксируется в журнале. Это не эквайринг и не фискальная система.

Закрытие блокируется при открытых/частичных заказах. Денежные исправления разрешены после закрытия. Изменение факта требует повторного открытия даты; сброс оплаченного факта блокируется до исправления оплаты.

## Сохранение и миграции

SQLite DB version2: state, history, draft. Миграция DB1→2 создаёт draft без удаления state/history. Данные schema1/2→3 преобразуются явно и сохраняют старые заказы и активность карточек. Профиль мясных групп применяется только к новой настройке.

Команда core создаёт новое состояние → проверка JS → native JSON/schema validation → транзакция → сверка expected revision → прежний снимок в history → новое состояние → пять последних history → COMMIT → подтверждение UI. Ошибки не показываются как «Сохранено». Защита ревизий локальная, не распределённая.

Draft — отдельная запись, автосохранение по изменениям/паузе. Восстановление только при совпадении ревизии. Парольные формы не входят в whitelist авточерновика. Аварийное восстановление history не удаляет базу автоматически: оператор выбирает предыдущую валидную запись и подтверждает.

## Лимиты и компромиссы

Один JSON-снимок: максимум 8 MiB; до 1000 дат, 20 000 клиентов/заказов, 300 позиций даты/заказа, 1000 карточек; audit до 10 000 записей. Это защитные пределы, не обещание скорости. Переписывается весь снимок; увеличение данных требует замера на устройстве и, вероятно, нормализованной SQLite. При достижении лимита журнал не обрезается молча — дальнейшая команда отклоняется; это будущая задача долговременного архива.

Фото: исходный файл до 10 MiB и 80M pixels, максимум 512px на длинной стороне, JPEG72, URI до 180 000 символов. Фото входит в общий снимок: десятки фотографий могут приблизить общий лимит. На телефоне импорт через Android SAF/Bitmap/ExifInterface ещё не проверен.

Backup: AES-256-GCM, PBKDF2-SHA256 210000, новый salt и IV, пароль не хранится. Шифруется экспорт, не SQLite целиком. История внутри телефона — не резервная копия от потери телефона.

25 Android instrumentation тестов подготовлены, но НЕ запущены. Тесты браузера с заменой хранилища не проверяют нативную реализацию.
